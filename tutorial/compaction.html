跳到稳定筛选讲解

FIELD NOTE 03 · MeshScan → MeshCompact

先决定留下谁，
再决定搬去哪。

从“每个位置都算一个答案”，走到“输出有多长、放在哪里，都由数据决定”。前缀和现在成了分配地址的工具。

固定手算示例 · 不是 WSE simulator 输出 · 本页不调用 SDK

← 前缀和入门 看一个例子 理解两个方向 跟着一条记录走 在本地试一次

01 · Stable stream compaction

去掉不需要的记录，
不打乱留下来的顺序。

假设只关心不低于 5 的读数。我们把其余读数去掉，让留下的记录连续排好；但不会排序，也不会把两个相同的值合并。这叫稳定筛选（stable stream compaction）。

它可以是传感器阈值筛选、稀疏数据预处理或活跃任务列表中的一个基础部件。这里实现的是这个部件，还没有连接真实传感器或生产系统。

02 · Count east, move west

先向右数清楚，
再向左搬整齐。

八条输入平均分给四个 PE，每个 PE 两条。每个 PE 的物理容量仍为三槽：有效输入数量不等于物理容量，多出来的槽不能参与筛选。

  1. 各自筛选每个 PE 只检查自己的有效输入。本地选中数依次是 [0,2,1,1]。
  2. 计数向东 →把累计选中数传给右边。收到的数叫 offset：在本 PE 之前，已经有多少条结果。
  3. 记录向西 ←算好每条记录的全局输出位置，再传送实际的值和原始下标。每个 PE 留下属于自己的记录，其余继续左传。

前缀和在这里回答的不是“总共加到多少”，而是：“我的第一条结果应该从哪个位置开始写？”

03 · 跟着 7@7 走一遍

它在 PE 3 出发，
为什么要住到 PE 1？

  1. PE 3 · 选中

    7 ≥ 5，所以保留。

    它的原始下标是 7，是 PE 3 本地第 0 条选中记录。前面三个 PE 一共选中 3 条，所以本 PE 的 offset 是 3。

  2. PE 3 · 定位

    新位置是 3，不是原来的 7。

    rank = 3 + 0 = 3；每个 PE 三槽，floor(3 / 3) = 1。因此目的地是 PE 1 的第 0 槽。

  3. PE 2 · 转发

    经过，不留下。

    PE 3 发来一条记录 (rank=3, value=7, index=7)。PE 2 发现 owner 为 1，把它和自己选中的 9@5 一起向西转发。

  4. PE 1 · 到达

    把 7 写入自己的输出第 0 槽。

    PE 1 留下 7@7；把 5@2、5@3、9@5 三条记录继续送给 PE 0。最终按物理 PE 和槽位回读，得到原顺序不变的结果。

包长不是写死的。

本例三条链路依次传 PE 3 → PE 2：1 条、PE 2 → PE 1：2 条、PE 1 → PE 0：3 条，方向都是向西。每个包先发记录数，再发对应的三元组；0 条记录只发包头，也要走完完成路径。

本例从东边收到的记录数是 [3,2,1,0]，向西转发数是 [0,3,2,1]。这是逻辑计数，不是性能测量。

为什么不用把数据往右搬？

筛选只删除记录，所以新位置 rank 不会大于原始下标。平衡连续输入分块中，第 p 个 PE 的下标小于 (p+1) × C，因此 floor(rank / C) ≤ p：记录只能原地留下或向左走。

这个性质依赖当前布局与稳定筛选。换成排序、扩张或哈希分区后，不能照搬这套单向返回协议。

04 · 项目的工程分量在哪里

不只是 filter，
还要证明每条记录都去了对的地方。

输出长度由数据决定
没有选中、全部选中、只有最后一个 PE 选中，都必须正确。输入值不相加，所以完整 int32 范围都可筛选，不受扫描基线的求和溢出限制。
一趟设备调用，多个异步阶段
Python 执行 H2D → 一次阻塞 compute → D2H；count 与 scatter 之间没有 host 往返。设备任务在收发完成后衔接下一步。
值、顺序、路由一起验算
C++ 独立串行筛选定义答案；分布式模型检查物理归属。host 检查值和原始下标、每 PE 计数、poison padding、完成与错误标记；不能只看最终条数。
每个 PE 都守恒
local_count + received_count = output_count + forwarded_count。以 PE 1 为例：2 + 2 = 1 + 3。没有凭空新增或消失的记录。

还要反复 launch，检查旧状态没有残留；超时、异常或 mismatch 都应产生失败，而不是成功报告。单个发送完成不是全局 barrier，必须等完整矩形的 blocking launch 返回，再回读并检查每个 PE。

现在的边界：这是有限批次（bounded batch），不是无限实时流服务；链式通信仍有顺序依赖，最坏转发量为 O(P×N)。这里只验证正确性，不声称真实硬件速度、加速比或生产部署。测试覆盖范围见 docs/COMPACTION_VALIDATION.md。

05 · 动手运行

先核对这一例，
再改一条你自己的规则。

以下命令在项目根目录中执行。先跑 C++ 对照模型，不需要启动 SDK：

make compaction
./build/meshcompact-reference --pes 4 --chunk-size 3 --threshold 5 --values 2,-1,5,5,-4,9,0,7
make test-compaction

找 JSON 的 output、indices 和 pes，逐一核对本页。接口允许 1–8 PE、每 PE 1–64 槽；允许的组合不等于每种组合都经过 SDK 测试。

运行真正的 SDK simulator

以下命令要求 Mac 上已配置 SDK 2.10.1 和名为 cs_sdk 的 Lima VM，并至少预留 4 GiB 磁盘空间。其他 VM 名或 SDK 路径可通过 python3 tools/run_compaction.py --help 查看配置选项：

limactl start cs_sdk
make simulator-compaction
limactl stop cs_sdk

保留私有 run 目录；以实际退出状态和验证报告为准。SDK、生成物、原始运行记录不放进公开网页。--prepare-only 只准备输入，不代表 simulator 通过。

沿着一条记录读源代码

  1. src/compaction.cpp先看正确结果与物理归属。
  2. src/compaction/layout.csl再看计数向东、记录向西的连接。
  3. src/compaction/pe.csl找 count、包头、payload、完成任务。
  4. host/compaction_contract.py核对 host 怎样发现错误。

完整数据契约和运行说明在 docs/COMPACTION.md；上面的源码路径均相对于项目根目录。

你自己的第一份改动

先手算 [1,9,2,8,3,7]、阈值 7、三个 PE、每 PE 三槽；然后加一个“只有最后一个 PE 选中”的测试。能解释后，把谓词改成闭区间筛选，同时改 C++、CSL 和测试。

保留原版本用于对照，一次只改变一个条件。记录预测输出、实际输出和对应代码，再解释改变筛选条件后，计数与路由为什么仍然成立。
